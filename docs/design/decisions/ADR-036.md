# ADR-036：事件提交后自动作废未决策请求，作废请求不可应答

## 状态
已采纳（2026-05-07）

## 背景
在基于 request/response 的任务驱动模型中，存在“迟到应答 / 并发应答”的天然竞态：

- 某个 request 已经触发了 emitterRules 产出内部事件并推进流程
- 但同一 task 下仍可能存在其他尚未提交 decision 的 request
- 这些 request 的迟到 decision 如果被写入，会污染规则脚本的聚合输入，产生不一致的审计与状态推进结果

因此需要定义“事件一旦被提交，未决策请求如何处理”的强约束。

## 决策
当某条 `emitterRule` 产出内部事件，并被引擎**提交**（写入 `WorkflowEvent` 且触发 `triggerEvent` 推进状态机）时：

1. 引擎必须将当前 `task` 下所有满足以下条件的 request 批量标记为作废（写入 `WorkflowRequest.voidInfo`）：
   - `voidInfo == null` 且
   - `responses` 中不存在 `kind="decision"` 的 response（即“尚未得到 decision 应答”的 request）

2. **作废的 request 不能被应答**：
   - 外部系统提交 response 时，若定位到的 `request.voidInfo != null`，则必须拒绝写入（例如返回 409/400，错误码 `REQUEST_VOIDED`）

3. 原子性要求：
   - “提交事件（event）”与“批量作废 pending-requests”必须处于同一原子更新中完成（同一 task 的乐观锁/事务边界内），避免出现事件已推进但旧 request 仍可应答的窗口期

## 备注
- 这里的“未决策请求”允许存在若干 `kind="update-task"` 的 response 日志；只要未出现 `kind="decision"`，就属于未决策请求。
- 若业务需要记录“业务应答时间”，应放入 `response.payload`，不影响本 ADR 的约束。
